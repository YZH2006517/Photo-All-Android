# Photo All 机型兼容记录

这份文档记录 Photo All 在各类安卓手机上踩过的坑：现象、查到的原因、最后的处理方式，以及从中总结出的做法。代码里对应的位置都写在条目里，方便以后排查同类问题时直接对照。

范围：Android 10（API 29）到 Android 17（API 37），Kotlin 应用加 C++ Vulkan 胶片引擎（vkdt filmsim 移植）。

---

## 一、总的经验

1. **先拿证据，再改代码。** 机型问题几乎都不能在开发机上复现，靠猜改出来的多半是绕路。先让应用自己把现场带回来：最后一步、相机状态、日志片段，看清楚再动手。OPPO 那次连改了 6 个版本，前 4 个都在降级绕路，直到报告里带上相机时间线，才看出是驱动在拍照瞬间重启。
2. **区分"真实设备"和"测试环境"。** 云测平台的手机经常对相机、传感器做了限制，连系统自带相机都拍不了。先用系统相机或别的第三方相机做个对照，再判断是不是自己的问题。
3. **降级要有依据，并且只降一次、记在这颗镜头上。** 例如"这颗镜头拍 RAW 会让驱动重启"这类结论，应基于明确的信号（错误码、时间点），记在 `camera_quirks` 里，下次直接走对的路。不要因为一次超时就把 RAW 关掉。
4. **一切可能卡住的地方都要有超时。** 相机回调、驱动编译、子进程绑定，厂商实现都可能永远不回调。卡住比报错更糟：用户只看到"按了没反应"。
5. **崩溃风险大的操作放进独立进程。** GPU 驱动编译着色器崩溃会把整个应用带走，放进 `:gpuprobe` 进程里先试一遍，失败就封存那项功能。
6. **报告要能截全。** 用户在手机上截图发来，所以精简显示：只保留应用自己的调用位置和每个异常的前两行，系统调用折叠成一行计数；复制按钮复制的仍是完整版。

## 二、按机型 / 芯片

| 机型 / 芯片 | 现象 | 原因 | 处理 |
|---|---|---|---|
| vivo（天玑，Mali GPU） | 第一次打开就闪退 | Mali 驱动编译多帧合成着色器 `hp_align.comp` 时崩溃 | 着色器重写为不用 subgroup 和局部数组（仍崩）；最终在独立进程里试编译，失败则封存多帧合成，RAW 改单帧 |
| OPPO PLG110（MT6993 ENG，Mali-G1-Ultra，Android 17） | 同上 Mali 编译崩溃 | 同上 | 同上，报告里显示"多帧合成：已封存" |
| OPPO PLG110（云测机） | 按快门没反应、"Camera is closed"、相机打开失败（4）、相机被移除（错误 8） | **云测机相机受限**，连系统相机都拍不了；表现为一发拍照请求驱动就重启 | 不是应用问题。期间加入的超时保护、重连推迟、相机时间线都保留 |
| OPPO（多款） | 拍照中离开应用，报 ImageCaptureException 错误 3（相机已关闭） | 生命周期停止时 CameraX 关相机，正在拍的那张被中止 | `CameraLife`：拍摄进行中保持 STARTED，拍完再跟随 Activity |
| OPPO（多款） | 测光闪光不闪 | 闪光模式下 HAL 返回 FLASH_STATE 未触发 | 从 FLASH_STATE 检测到后，改为在该帧常亮 LED，按镜头记住（`flash_torch_<id>`） |
| Samsung（Android 14+） | 检测进程误判 GPU 不可用 | `FreecessController` 冻结后台，`bindService` 返回 false | 等待连接回调；进程没起来判为 `unknown`，不缓存、不封存 |
| Samsung | "AF-C" 被换成两行 | 三星系统字体偏宽 | 相关文字 `isSingleLine = true` |
| Samsung S23（SM-S9180，Adreno 740） | 拍摄设置里切主题时报"View not attached to window manager" | 切主题会重建界面，底部面板的淡出动画还在调用已销毁窗口的 `setDimAmount` | 切主题前立即关闭面板（`dismissNow`），动画先确认窗口还挂着 |
| Xiaomi M2007J17C（SM7250 骁龙 765G，Adreno 619，Android 12） | 切到零延迟 RAW 时连报"相机打开失败（2）"；6 帧 HDR+ 冲洗时原生闪退（SIGSEGV，`vkCmdCopyImageToBuffer`） | ① CameraX 解绑后相机还没真正关掉，Camera2 立刻打开得到 `ERROR_MAX_CAMERAS_IN_USE`。② 多帧合成的某次提交失败（多半是 device lost 或显存不足），循环 break 后仍把拷回命令录进已失效的命令缓冲区，驱动空指针 | ① 错误 1/2（被占用）时隔 300 / 700 / 1500 ms 重开。② 提交失败后不再录命令，改为报错；多帧失败时（device lost 先重建引擎）只用第 1 帧重冲，照片不丢。HDR+ 改为只能在设置里打开，默认关并先提示兼容风险 |
| Xiaomi 14 | 用 CCD 风格冲洗后闪退 | digicam 效果的临时缓冲区堆溢出 | 修正缓冲区尺寸 |
| Xiaomi 11 Ultra（第三方 ROM） | RAW 冲洗失败 | DNG 用了 lossless JPEG 压缩（条带或分块），样本位深 8–16 位不等 | DNG 读取器支持这些格式；仍读不了的镜头改 JPEG（`raw_unusable_<id>`） |
| 大底传感器（vivo X300 Pro、OPPO Find X9 Pro、Xiaomi 5000 万像素机型） | 内存暴涨、被系统杀掉 | 支持列表里有全尺寸输出，连拍或解码一次就是几个 GB | 静态照片上限约 2600 万像素；零延迟 RAW 优先取合并后的尺寸，缓冲环按内存限帧数（约 600 MB）；JPEG 按工作尺寸解码 |
| 部分天玑机型 | 闪光不触发 | 同 OPPO | 同上 |

## 三、按问题类别

### 1. GPU 与 Vulkan 引擎

- **Mali 着色器编译崩溃。** 驱动在 `vkCreateComputePipelines` 里直接崩溃，捕获不到。
  - 做法：`GpuProbe` 在 `:gpuprobe` 进程里完整创建一次引擎，结果分三种：`ok`、`sealed: <阶段>`、`unknown`。只有前两种会缓存。
  - 每一步编译都记录阶段（`set_stage_hook` → `FilmNative.stage`，写盘用 `commit()`），驱动崩了也能留下是哪个 kernel。
  - 封存后 `FilmEngine.create(…, burst_kernels = false)` 跳过 `hp_*` kernel，多帧合成改单帧。
- **取景器 GLES 和引擎 Vulkan 抢同一个编译器。** Mali 上两边同时编译容易出事，用 `shaderCompileLock` 串行。
- **提交失败后命令缓冲区就作废了。** 分批 `submit_and_wait` / `begin` 任一步失败，后面不能再往 `cmd` 里录任何命令，否则 Adreno 驱动直接空指针崩溃（不是返回错误）。失败路径一律跳过剩余录制。
- **AGSL 需要 API 33。** minSdk 是 29，所以界面特效没用 AGSL，改用 Canvas 加烘焙好的渐变。

### 2. 相机（CameraX / Camera2）

- **绑定失败要逐级降级，不能让异常冒到主线程。** 顺序：预览加拍照加测光分析 → 去掉测光分析 → JPEG → 报"相机启动失败"。每一级都记进报告。
- **不能只看"绑定成功"，要看相机的真实状态。**
  - 现象：0 号主摄从系统列表消失又回来时，CameraX 新建了相机对象，而我们的用例还挂在旧的上，拍照请求挂起，日志是 `useCaseCamera is null`。
  - 做法：监听 `cameraInfo.cameraState`；绑定后 4 秒还没打开就重连（最多 3 次）；`CameraManager.AvailabilityCallback` 报自己的镜头重新可用时，如果相机没开就重连；快门前确认相机已打开，没开就不发请求。
- **拍照途中绝不重连。** 重连会关掉相机，正在拍的那张直接报"Camera is closed"。`bindCamera()` 在 `capturing` 时只记下来源，等拍完再执行。
- **拍照超时（`ShotWatch`）。** 请求帧、开始曝光、已保存，每一步都重新计时（8 秒加 3 倍曝光时间）。超时后结束这张、重连、生成报告；之后迟到的回调一律丢弃。
- **驱动重启的识别。** 按快门 3 秒内相机被移除（`CameraState` 错误 8），判定为驱动在 RAW 请求上重启：
  - 第一次：改用最简参数，不再请求镜头暗角图和固定色调曲线（`raw_plain_<id>`）；
  - 第二次：这颗镜头改 JPEG。

  驱动重启期间等原镜头回来（最多 8 秒），不要切到别的镜头。
- **Camera2 RAW 有两种取法。**
  - HDR：连续请求里就带 RAW 流，零延迟取环里的帧。部分芯片不支持连续输出全尺寸 RAW，会报设备错误。
  - 单张：连续请求只喂预览和测光，按快门时发一次 `TEMPLATE_STILL_CAPTURE` 取 RAW（`ZslCamera.onDemand`）。
  - 建会话前用 `isSessionConfigurationSupported`（API 31+）问一下输出组合；不支持就去掉测光流。会话 6 秒没建好要报出停在哪一步。
- **配置变化不要让系统重建相机界面。** 深色模式自动切换、显示大小、字体、语言、折叠屏开合，都会让系统重建 Activity 并关掉相机。
  - 做法：在 `configChanges` 里声明这些变化，自己处理；需要重建时，如果正在拍照就等拍完再 `recreate()`。
- **非 RAW 拍摄请求固定的 sRGB 色调曲线（`TONEMAP_PRESET_CURVE_SRGB`）。** 这样 JPEG 和取景器预览用的是同一条曲线，取景器上套的胶片 LUT 才和成片对得上。所以 JPEG 拍摄不做导入时那种"场景还原"。
- **闪光照片的亮度对齐。** HAL 定的闪光曝光往往比取景器暗，闪光灯照不到的背景发灰。改为"只提亮"：向取景器亮度靠，但不压暗，最亮的 0.5% 不超过 0.9，最多提 3 档（`stage match lift`）。

### 3. 导入照片（8 位、已渲染的 JPEG）

- 手机 JPEG 已经带了手机自己的饱和、反差，高光也截在 1.0；再叠胶片的 S 曲线，反差翻倍，高光发平发灰。
- 做法：在解码入口做"场景还原"，在线性光里：
  - 饱和度降约 12%；
  - 中灰附近的反差降约 14%；
  - 用有理函数肩部的反函数把高光推回 1.0 以上，余量随过曝比例在 +1.2 到 +2.5 档之间；
  - 在线性数据上用中央重点测光，做一半的自动曝光，最多 ±0.75 档。

  参考 SpektraLab 的原则（入口处转成场景线性、在线性数据上测光），公式是自己写的。
- 外部软件导出的图片无法逆推回场景光，只能按"典型手机渲染"做固定的还原，不追求精确反演。

### 4. HDR 输出（EDR / Ultra HDR）

- `Bitmap.setGainmap` 和 `Bitmap.compress` 生成 JPEG/R 需要 API 34；更低版本不加增益图，不影响 SDR 成片。
- `ExifInterface.saveAttributes` 写 EXIF 时，会把 SOS 之后的数据原样拷贝，附在后面的增益图 JPEG 保得住；MPF 里的偏移是相对值，主图变长也不影响。已用文件结构核对过。
- 查看器和导入预览要设 `window.colorMode = COLOR_MODE_HDR`，否则只显示 SDR。
- 原图本身是 Ultra HDR（例如三星 S23 拍的）时，直接读它的增益图作为"场景高光"的依据。

### 5. 界面与系统

- **全面屏和挖孔。** 所有界面的边距都用 `systemBars() or displayCutout()`；底部面板加上导航栏高度；横屏两侧面板宽度按"4:3 取景剩下的宽度"算，限定在 150–210 dp。
- **对话框动画与界面重建。** 界面可能在动画中途被重建，动画回调里要先确认窗口还在（`decorView.isAttachedToWindow`）。
- **PixelCopy。** 部分系统皮肤永远不回调相机画面的 PixelCopy，只当锦上添花用，要有不依赖它的退路。
- **触感。** 部分马达不支持振幅控制，要用不依赖振幅的效果。

## 四、诊断手段

| 手段 | 位置 | 用途 |
|---|---|---|
| 问题报告（下次启动弹出） | `CrashReport` / `ui/CrashReportSheet.kt` | 机型、芯片、GPU、系统、内存、最后一步、堆栈；原生崩溃读 tombstone |
| 最后一步 | `CrashReport.stage()` | 每个关键步骤写盘；崩溃或卡住时就知道停在哪 |
| 相机时间线 | `CameraActivity.trail()` | 最近 16 件事：重连及其来源、相机状态变化、每次按快门时相机的状态 |
| 相机日志片段 | `cameraLogTail()` | 卡住时读取本进程最近的相机相关日志（CameraX、camera-pipe、厂商标签），排除应用自己的行 |
| 照片冲洗记录 | `files/photo_info/<文件名>.json` | 每张照片的曝光、白平衡、RAW 数据、引擎参数和各步用时 |
| 诊断信息 | 设置 → 复制诊断信息 | 每颗镜头的 RAW、闪光、自动曝光能力，已学到的设备记忆，最近的提示 |

### 设备记忆（`camera_quirks`）

| 键 | 含义 | 何时写入 |
|---|---|---|
| `flash_torch_<镜头>` | 测光闪光不触发，改为常亮 LED | 拍完发现 FLASH_STATE 未触发 |
| `raw_unusable_<镜头>` | 这颗镜头改用 JPEG | DNG 读不了，或最简参数下 RAW 仍让驱动重启 |
| `raw_plain_<镜头>` | RAW 请求不带镜头暗角图和色调曲线 | 第一次 RAW 让驱动重启 |
| `raw_camera2` | 单张 RAW 走 Camera2 按需取 | 相机开着，但 CameraX 的 RAW 请求超时 |
| `zsl_blocked` | 这些镜头不走零延迟 RAW，HDR 改普通连拍 | 镜头拒绝连续输出 RAW 和预览 |
| `stall_reset_v39` | 一次性清理旧版本的误判降级 | beta39 启动时 |

GPU 相关的记忆在 `CrashReport` 偏好里（`burst_off`）和 `GpuProbe` 的结论缓存里。

## 五、排查流程（下次遇到新机型问题）

1. 让用户发问题报告的截图（精简版一到两屏就够），先看"最后一步"和相机时间线。
2. 判断类型：
   - 原生崩溃：看 tombstone 和引擎阶段，多半是 GPU 驱动。
   - 卡住没反应：看停在哪一步。
   - 报错：看错误码和时间点，是谁先动的手。
3. 让用户用系统相机或别的第三方相机做对照，排除受限设备。
4. 证据不够时，先发一个只加诊断、不改行为的版本，不要直接降级。
5. 确定原因后，修复要具体到这一类设备，必要的降级记进设备记忆，并在提示里说清楚原因。
6. 用真机（目前是三星 S23）回归一遍正常流程，确认修复没有影响其他机型。
